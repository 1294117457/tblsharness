# 03 推荐方案详细设计

> 方案 E：默认路径指向 `globalStorage/bin/tbls`，首次激活按平台 / 架构从 GitHub Releases 下载；找不到 / 校验失败时退回引导；用户可手动覆盖。

## 一、默认 tbls 的放置位置

放在 `context.globalStorageUri` 下的固定路径：

```
<globalStorage>/
└ bin/
     └ tbls[-vX.Y.Z][-platform-arch]/
          └ tbls(.exe)
```

- `globalStorageUri` 是 VS Code / Cursor 给每个扩展分配的目录（Windows 上类似 `%APPDATA%\Cursor\User\globalStorage\harness.cursor-harness`），**对扩展可写、对其他应用隔离**。
- 用带版本号的目录名 `tbls-1.96.0-windows-amd64/`，允许并存多个版本（升级时下载新版、下次启动启用，旧版保留供回退）。
- 当前启用版本记录在 `<globalStorage>/tbls.current.json`：

  ```ts
  interface CurrentTbls {
    version: string;       // '1.96.0'
    path: string;          // 'bin/tbls-1.96.0-windows-amd64/tbls.exe'
    sha256: string;        // 下载回来算的，便于排查
    downloadedAt: string;   // ISO 时间
  }
  ```

## 二、首次激活时的下载流程

`extension.ts` 的 `activate` 中：

```
const status = await ensureTbls(context);
```

`ensureTbls(context)` 步骤：

1. 读 `tbls.current.json`：如果存在且文件还在、sha256 一致、`runner.probe()` 跑得通（执行 `--version`），什么都不做。
2. 否则判断 `process.platform` / `process.arch`，得到 `target`：

   | OS | arch | GitHub asset 模板 |
   | :-- | :-- | :-- |
   | `win32` | `x64` | `tbls_VERSION_windows_amd64.zip` |
   | `darwin` | `arm64` | `tbls_VERSION_darwin_arm64.tar.gz` |
   | `darwin` | `x64` | `tbls_VERSION_darwin_amd64.tar.gz` |
   | `linux` | `arm64` | `tbls_VERSION_linux_arm64.tar.gz` |
   | `linux` | `x64` | `tbls_VERSION_linux_amd64.tar.gz` |
   | 其他 | — | 跳到引导 UI |

3. 拉 GitHub Releases 元数据（`https://api.github.com/repos/k1LoW/tbls/releases/latest`），找匹配 `tag_name`（如 `v1.96.0`）和 `target` 的 `browser_download_url`。
4. 下载到临时目录，校验 sha256（从元数据里读；如果元数据没给 sha256，记录 warn 但不阻止）。
5. 解压（zip / tar.gz）出单个二进制，移到 `bin/tbls-VERSION-target/tbls[.exe]`，加可执行位（Windows 跳过）。
6. 写 `tbls.current.json`，清空 `tbls.disabled` 标记。

**联网失败 / GitHub 不通 / 资产找不到** → 不报错（首次激活不应该卡住），把"未配置"状态返回；后续调用 `tblsOutJson` 走兜底路径。

**不会做**：

- 不会在用户机器上**预装**任何东西到 `PATH` / `Program Files` / `usr/local`；一切都在 `globalStorage` 里，卸载扩展时随扩展一起清掉。
- 不会做**自动更新**。tbls 升级通过"检查新版本"按钮触发，由用户决定。

## 三、`harness.tblsPath` 设置的语义变化

当前：默认 `"tbls"`，意味着"在 PATH 里找名为 `tbls` 的可执行文件"。

新语义：

| 取值 | 行为 |
| :-- | :-- |
| 空字符串 `""`（**新默认**） | 用插件内置的 `globalStorage/.../tbls`；首次激活自动下载 |
| 绝对路径 `"C:\tools\tbls.exe"` | 按这个路径执行（行为和现在一样） |
| PATH 里的可执行名 `"tbls"` / `"/usr/bin/tbls"` | `execFile` 会按文件名在 PATH 里找（保留旧行为，方便老用户） |

迁移：

- 旧设置里**填了路径的用户**继续用原路径，不受影响。
- 旧设置**保持默认 `tbls`** 的——下次升级插件后，运行时检测到 `harness.tblsPath === "tbls"`（默认的旧值），等价于新默认 `""`，提示用户"已为您下载 tbls 1.96.0，使用内置版本"。不强制改。

> 这一段也写在迁移说明里给用户看。考虑到很多用户其实没动过这个设置（即 `tblsPath` 等于 `tbls`），默认行为从 `PATH 查找` 改为 `内置下载版本` 是用户可见的变化——文档要说清楚。

## 四、用户主动指定路径

设置面板的 `harness.tblsPath` 旁边增加：

- **浏览…**：弹文件选择框，按平台过滤（Windows 选 `*.exe`，其他平台无后缀过滤）。用户选完直接写入设置。
- **测试当前配置**：按钮，立刻跑 `tbls --version`，结果显示在设置项下方（"当前使用：C:\...\tbls.exe · 版本 1.96.0"，或红字失败原因）。

`harness.tblsPath` 的描述改为：

> tbls 可执行文件。留空使用插件自动下载的内置版本；填绝对路径或 PATH 中的可执行名（如 `tbls`）改用您机器上的版本。

## 五、命令

| 命令 | 触发方式 | 行为 |
| :-- | :-- | :-- |
| `harness.tbls.checkUpdate` | 命令面板 / 设置页按钮 | 检查 GitHub Releases 上是否有新版本。流程：拉 latest → 与 `tbls.current.json` 对比 → 若有新版本，弹"下载并启用 X.Y.Z？"对话框；用户确认后下载到新目录、切换 `tbls.current.json` 指向新版；旧版保留 5 个版本，再老的清理 |
| `harness.tbls.repair` | 命令面板 / 设置页按钮 | 清掉当前 `tbls.current.json`，重新走"首次激活下载"。用于：内置版本坏了、用户想换平台（如远程 SSH 后架构变了）、手动清缓存 |
| `harness.tbls.openFolder` | 命令面板 / 设置页按钮 | 在系统资源管理器里打开 `<globalStorage>/bin/` 目录，让用户看到 / 删 / 替换 |

不新增"右键功能"——这些命令通过命令面板 + 设置页按钮入口就够。

## 六、错误兜底：找不到 tbls 时的引导

`runner.ts` 的 `ENOENT` 处理路径保持不变，但 `connection/errors.ts` 的识别结果 `action: 'setTblsPath'` 之外，新增 `action: 'downloadTbls'`：

```
找不到 tbls 可执行文件。                          [操作]
```

按钮（按行 + 顺序）：

1. **下载内置版本（推荐）** —— 走 `harness.tbls.repair`，下载到 `globalStorage/bin/`，完事后再跑一次当前的连接 / 同步。
2. **选择本地文件…** —— 弹文件选择框，写入 `harness.tblsPath`，跑一次。
3. **在终端安装 tbls…** —— 弹**只读**终端（VS Code 内置），预置 `brew install tbls` / `scoop install tbls` / `go install github.com/k1LoW/tbls/cmd/tbls@latest` 三行命令，按用户机器显示对应的（macOS → brew；Windows → scoop + go install；Linux → go install 提示"如果你的发行版没有包，可以 go install"）。
4. **打开 tbls 下载页** —— `vscode.env.openExternal('https://github.com/k1LoW/tbls/releases/latest')`。

按推荐度排序。每个按钮执行后自动重试当前的失败操作（连接 / 同步）。

## 七、Runner 改动

`tblsOutJson` 的 `tblsPath` 入参不变——是外面传进来的字符串。

新增一个 `resolveTblsPath(context, configured): string`，给调用方 `connectionPanel.ts` 和 `db.ts` 用：

```ts
async function resolveTblsPath(context, configured): Promise<{
  path: string;
  source: 'bundled' | 'user' | 'path';
}> {
  if (configured) return { path: configured, source: configured.includes('/') || configured.includes('\\') ? 'user' : 'path' };
  const current = readCurrent(context);
  if (current) return { path: absolute(context, current.path), source: 'bundled' };
  // 没下载过，下载
  const downloaded = await ensureTbls(context);
  if (downloaded) return { path: downloaded, source: 'bundled' };
  // 下载失败，抛错让上面走引导
  throw new TblsError('tbls 未安装，且自动下载失败', 'notFound');
}
```

调用方把 `resolved.path` 传给 `tblsOutJson`；不再自己读 `config.get('tblsPath')`。

## 十、隐私与安全

- 只从 GitHub Releases 拉（`api.github.com` + `objects.githubusercontent.com`，都是 GitHub 标准域名，不引入第三方源）。
- 下载文件校验 sha256（从 GitHub API 元数据读 `digest` 字段）；元数据没给 sha256 时记录 warn，不阻止——但可以接受这个降级，因为来源是 GitHub Releases。
- 用户随时可以把 `harness.tblsPath` 改回自己机器上的版本，插件不会再覆盖。
- 不收集任何遥测；不联网只发 `tbls --version` 检查是否可用。
- 不静默修改 `PATH` / 系统级安装位置；一切都在扩展自己的目录里。

## 十一、明确不做的事

- ❌ **不**内置"tbls 自动更新"。tbls 升级靠 `harness.tbls.checkUpdate` 按钮。
- ❌ **不**自动改用户机器的 `PATH`。即使用户点了"在终端安装 tbls…"，也只是打开一个预置命令的终端，不真的执行。
- ❌ **不**做"按 tbls 的 use case 自动选数据库驱动"——这是 [03-tbls-capability.md](../02新增设置/03-tbls-capability.md) 提到的扩展机制，不属于本次范围。
- ❌ **不**重写 `tblsPath` 解析逻辑让 `runner.ts` 知道内置版本的事——`runner.ts` 仍然只接收字符串；判断在哪一层做见 [04-影响范围和实现计划.md](./04-影响范围和实现计划.md)。
