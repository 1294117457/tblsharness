## 问题一：去掉双击画布空白处自动新建设计表

### 1.1 现状

| 入口 | 行为 |
| :-- | :-- |
| 双击画布空白处（`CanvasView.vue onDoubleClick`） | 在根画布的鼠标位置新建一张设计表 |
| 双击分区框内部空白处（`onNodeDoubleClick`，partition 且非标题区域且未折叠） | 在该分区的鼠标位置新建一张设计表 |
| 工具栏"+ 新建表"按钮的 title | 提示"也可以双击画布空白处" |
| 画布空状态文案 | "双击空白处新建表" |

双击创建容易误触发：用户想聚焦某个区域（快速双击缩放）或选中文本时，意外地创建了一张空表。对于新手，更常见的操作路径是从工具栏、右键菜单或属性面板新建，双击快捷方式带来的便利不如误触的代价。

### 1.2 期望

- **去掉双击画布空白处新建表的功能**。
- **去掉双击分区框内部空白处新建表**。双击分区框标题仍然是聚焦（不变）。
- 工具栏按钮去掉"也可以双击画布空白处"的 title 提示。
- 空状态文案改为不再提及双击。

### 1.3 涉及的改动

| 文件 | 改动 |
| :-- | :-- |
| `CanvasView.vue` | 删除 `onDoubleClick` 函数及 `.canvas` 上的 `@dblclick`；`onNodeDoubleClick` 中去掉 partition 内部空白新建表的分支（只保留双击标题/折叠框 = 聚焦，双击 diagram = 编辑文本） |
| `App.vue` | 删除 `@create-table="(level, p) => void createTable(level, p)"`（CanvasView 不再 emit `create-table`）；去掉工具栏按钮 title 里的"也可以双击画布空白处"；空状态文案改为"在工具栏或右键菜单中新建表" |
| `CanvasView.vue` emit | 去掉 `'create-table'` emit 声明 |

> 注意：右键菜单"在这里新建表"保留，这是有意识的操作。

## 问题二：分区画布增加手动调整大小功能

### 2.1 现状

| 项目 | 现在 |
| :-- | :-- |
| 分区框大小 | **纯自动计算**：`viewModel.ts buildView` 从内到外遍历所有子内容，取包围盒 + `PART_PAD`，和 `PART_MIN` 取较大值。`CanvasPartition` 接口只有 `x, y`，没有 `width, height`。 |
| 移动 | 拖拽 header 栏可以移动（`dragHandle: '.header'`），已实现 |
| 调整大小 | **不支持**。分区框的大小完全由内容决定，用户不能手动改变宽高 |

问题：

1. 空分区画布只有 `PART_MIN`（320×160）的大小，太小，用户无法预先圈出一块区域然后往里放内容。
2. 分区框边距太紧（只有 `PART_PAD = 24`），想在框内留白让布局更宽敞时做不到。
3. 用户无法统一几个分区的大小来对齐排列。

### 2.2 期望

- 分区框支持**手动调整大小**，和设计图卡片 `DiagramNode.vue` 一样用右下角拖拽手柄。
- 手动设置的宽高存入 `CanvasPartition`（`width?`, `height?`）和 `layout.json`；没有设置时仍按内容自动计算（向下兼容）。
- 最终大小 = `max(手动宽高, 内容包围盒 + padding, PART_MIN)`，即手动设置的值是**下限**，内容超出时框自动撑大。
- 折叠状态下不能调整大小（大小固定为 `PART_COLLAPSED`）。
- 分区框标题栏（header）以外的区域也可以直接移动。
  - 当前的 `dragHandle: '.header'` 限制了只能从 header 拖动。去掉这个限制，让用户可以从分区框的任意位置开始拖动（只要不是在子节点上）。
  - 这让空分区框和大分区框更易操作。

### 2.3 方案

#### 2.3.1 数据结构

`shared/canvas.ts`：

```typescript
export interface CanvasPartition {
  id: string;
  name: string;
  description?: string;
  parent?: string;
  x: number;
  y: number;
  /** Manual minimum width; actual width is max(this, content bounding box). */
  width?: number;
  /** Manual minimum height; actual height is max(this, content bounding box). */
  height?: number;
  collapsed?: boolean;
  namespace?: CanvasNamespace;
}
```

`serializeCanvas` 序列化时保留 `width`/`height`；`parseCanvas` 读取时也保留（可选字段，向下兼容）。

#### 2.3.2 大小计算

`viewModel.ts buildView` 的分区框大小计算改为：

```
contentWidth  = max(contentRight + PART_PAD, PART_MIN.width)
contentHeight = max(contentBottom + PART_PAD, PART_MIN.height, PART_HEADER + PART_PAD)
finalWidth  = max(partition.width ?? 0, contentWidth)
finalHeight = max(partition.height ?? 0, contentHeight)
```

#### 2.3.3 调整大小交互

`PartitionNode.vue`：

- 未折叠时，右下角显示调整大小手柄（复用 `DiagramNode.vue` 的 `.resize` 样式）。
- 拖拽手柄时：
  1. `pointerdown`：记录起始位置和当前 `width/height`。
  2. `pointermove`：计算新的 `width/height`（`max(PART_MIN, 起始值 + delta / zoom)`），更新 draft 显示。
  3. `pointerup`：emit `resize` 事件。
- `CanvasView.vue` 收到 `resize` 事件后，发 `partition.put` op 更新 `width`/`height`。

#### 2.3.4 移动

`CanvasView.vue rebuild` 中分区节点：

```diff
- dragHandle: '.header',
```

去掉 `dragHandle`，分区框的任意非 `nodrag` 区域都可以拖动（header 里的按钮已有 `nodrag` class）。

> 注意：分区框内的子节点自己处理拖拽，不会穿透到分区框上。只有点击分区框本身的空白区域才会开始拖动分区框。

### 2.4 需要注意

- **自动布局**（`layoutLevel`）计算的是节点坐标，不改 `width/height`。布局完成后分区框大小仍由自动计算 + 手动下限决定。
- **双击标题聚焦**时，`focusOn` 会算分区框的 bbox，用的是 `PartitionView.width/height`（已含手动值），不需要额外改动。
- 拖入拖出分区框时，框大小会因内容增减自动变化（超出手动值时撑大，低于手动值时回到手动值）。
- **ELK 布局时**给 partition 节点的尺寸应使用手动宽高（如果有），否则用 `PART_MIN`。

### 2.5 涉及的改动

| 文件 | 改动 |
| :-- | :-- |
| `shared/canvas.ts` | `CanvasPartition` 加 `width?`、`height?`；`serializeCanvas` 保留这两个字段 |
| `canvas/viewModel.ts` | 大小计算取 `max(手动值, 内容包围盒)`；`PartitionView` 不需要改（已有 `width`/`height`） |
| `PartitionNode.vue` | 加右下角调整大小手柄（`.resize`），emit `resize` 事件 |
| `CanvasView.vue` | 收 `resize` 事件 → `partition.put`；去掉分区节点的 `dragHandle: '.header'` |
| `canvas/layout.ts` | `layoutLevel` 的 partition 节点尺寸优先用手动值 |
| `test/canvas.test.ts` | 加 `partition.put` 含 `width/height` 的测试 |

## 问题三：拖动节点到分区画布边缘时闪烁

### 3.1 现状

把一张设计表或设计图从根画布拖到分区框上方时，还没松开鼠标，轻微移动鼠标，会看到节点在"进入分区"和"回到根画布"之间来回闪烁。

### 3.2 原因分析

闪烁涉及三个互相触发的机制：

1. **`onNodeDrag`**（`CanvasView.vue` 388–392）：每次鼠标移动时用 `centerOf(node)` 算节点中心的绝对坐标，然后用 `frameAt` 检查这个点在哪个分区框内。如果 `target !== levelOf(node.id)`，设置 `dropTarget`。

2. **`rebuild` 触发**（198–201）：`dropTarget` 是 `ref`，`watch([state.selection, dropTarget.value], () => rebuild())` 会在 `dropTarget` 变化时触发整个节点数组重建。

3. **边界抖动**：在分区框边缘拖拽时，`centerOf` 返回的坐标在每次鼠标微动后可能在框的边界内外跳动。这导致 `frameAt` 交替返回"在框内"和"不在框内"，于是 `dropTarget` 快速在 `partN ↔ undefined` 之间切换，每次切换触发 `rebuild()`。重建节点数组后 Vue Flow 更新 DOM，`computedPosition` 可能产生细微偏移（因为 Vue Flow 在 rebuild 时可能会短暂重置拖拽状态），导致下一帧 `centerOf` 的结果又变了，形成循环。

核心问题：**拖拽检测点（`centerOf`）与分区框的精确边界做比较，没有任何防抖或迟滞（hysteresis）**。在边界附近，1px 的鼠标抖动就足以导致判断翻转。

### 3.3 方案

**用迟滞（hysteresis）取代精确边界检测**：进入分区需要节点中心进入边界**内侧一段距离**，离开分区需要节点中心离开边界**外侧一段距离**。一旦进入后，在边界附近的微小移动不会触发反复切换。

具体做法：

```
DRAG_ENTER_INSET = 16   // 要"进入"一个分区，节点中心必须在框边界内侧 16px 以内
DRAG_LEAVE_OUTSET = 16  // 要"离开"当前拖拽目标，节点中心必须超出框边界外侧 16px
```

修改 `onNodeDrag` 的逻辑：

```typescript
onNodeDrag(({ node }) => {
  const center = centerOf(node);
  const exclude = excludedFor(node);
  const current = dropTarget.value;

  if (current) {
    // 已经有拖拽目标：检查是否离开（用宽松边界）
    const r = absRect(`part:${current}`);
    if (r && center.x >= r.x - DRAG_LEAVE_OUTSET
          && center.x <= r.x + r.w + DRAG_LEAVE_OUTSET
          && center.y >= r.y - DRAG_LEAVE_OUTSET
          && center.y <= r.y + r.h + DRAG_LEAVE_OUTSET) {
      return; // 仍在宽松边界内，不变
    }
  }

  // 检查进入（用严格边界）
  const target = frameAtInset(center, exclude, DRAG_ENTER_INSET);
  const next = target !== levelOf(node.id) ? target : undefined;
  if (next !== dropTarget.value) dropTarget.value = next;
});
```

其中 `frameAtInset` 是对 `frameAt` 的修改版，在判定 `point` 是否在框内时，四边各向内收缩 `inset` 像素：

```typescript
function frameAtInset(point: Position, exclude: Set<string>, inset: number): string | undefined {
  let best: string | undefined;
  let bestDepth = -1;
  for (const p of props.view.partitions) {
    if (p.collapsed || exclude.has(p.id)) continue;
    const r = absRect(`part:${p.id}`);
    if (!r) continue;
    if (point.x < r.x + inset || point.x > r.x + r.w - inset
     || point.y < r.y + inset || point.y > r.y + r.h - inset) continue;
    if (p.depth > bestDepth) { best = p.id; bestDepth = p.depth; }
  }
  return best;
}
```

这样，进入时需要比精确边界多走 16px，离开时需要多走 16px，总共 32px 的迟滞带。在这个带内移动不会触发 `dropTarget` 变化。

另外，减少 `rebuild` 的触发频率：

```diff
  watch(
-   () => [state.selection, dropTarget.value],
+   () => state.selection,
    () => rebuild(),
  );
```

`dropTarget` 的变化只需要更新分区框的样式（高亮），不需要重建整个节点数组。把 `dropTarget` 从 rebuild 触发器里拿掉，改为 `PartitionNode` 接收 `dropTarget` prop 后只更新自己的 CSS class（现在已经是这样传递的，不需要 rebuild）。

### 3.4 涉及的改动

| 文件 | 改动 |
| :-- | :-- |
| `CanvasView.vue` | 新增 `frameAtInset` 函数；`onNodeDrag` 加迟滞逻辑；`watch` 不再因 `dropTarget` 触发 `rebuild` |
| `PartitionNode.vue` | 不需要改（`dropTarget` 已作为 prop 传入） |

### 3.5 为什么不用防抖（debounce）

防抖（只取最后一次值）会导致 `dropTarget` 延迟更新，拖拽时视觉反馈变慢。迟滞方案在边界处**不更新**而不是**延迟更新**，远离边界时响应依然是即时的。
