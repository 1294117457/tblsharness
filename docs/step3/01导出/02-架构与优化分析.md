## 1. 一句话定位

Harness 是一个 VS Code / Cursor 插件，把 **tbls 的 JSON** 当作"设计库 / 数据库 / 设计图"三方的统一数据格式，让用户在画布上**只编辑设计**、**只读地对照数据库结构**、**通过设计图与 AI 协作**，从不连进数据库写一行。导出给 AI（第三阶段第一步）把这个模型直接落成可被 AI 读取的目录。

### 2.1 这套分层贯彻到什么程度

| 边界 | 谁在守 | 怎么守 |
|:--|:--|:--|
| shared 不可依赖 vscode | CI 不跑，靠纪律 | 文件顶部 `import * as vscode` 出现 = 违规；测试里 import 不下不动 |
| 领域层不可直接写盘 | 边界面包一层 | `export/builder.ts` 是纯函数，落盘是 `export/run.ts`；`canvasEditor.ts` 把 `applyCanvasEdit` 调用结果变成 Webview 写盘 |
| Webview 不可信 | 协议 + 主进程再算 | 所有 `design/edit` / `items/move` / `export/run` 都由主进程按 `ModelStore` 重新求值；webview 只能传 key / id |
| 不可泄漏连接信息 | 一条注释 + 测试锁 | `model/store.ts:55-58` 明确写 `dbName()` 不可面向 AI；`test/exportBuilder.test.ts` 锁 db 条目只含 `source` 字段 |
| 不可写数据库 | 物理上不连 | 设计库 / 数据库两条 `source` 在 model 上是同一类对象，但只有 db 才允许被 `tbls` 读、写操作全走设计 ops 路径 |

### 2.2 一条主线：所有交互最终落到两类动作

整个插件的功能再花哨，最终都收敛到两条动作：

1. **`applyDesignOps(doc, ops)`** —— 改设计库的 schema/ext（`src/shared/designOps.ts`）
2. **`applyCanvasEdit(canvas, edits)`** —— 改画布的 layout（`src/shared/canvas.ts`）

第 1 类由"属性面板编辑 / 同步 ER 图 / 快速添加字段 / 复制数据库表 / 改名"驱动；第 2 类由"新建表/图/分区 / 拖拽 / 折叠 / 调整大小 / 隐藏 / 跨层移动"驱动。其它一切 —— 树、对比、面板、状态、通知 —— 都是这两类动作的"视图"或"触发器"。

## 4. 关键设计决策（为什么这样、不是那样）

> 这一节挑出"如果接手后想动，先想清楚再动"的几个决定。

1. **tbls JSON 是单一真理，不是 tbls 数据库。** 读出来的 JSON 存成快照，但**写路径只改 schema.json / ext.json / layout.json**。tbls 子进程**只用于读**。`tbls/runner.ts` 是只读调用器，没有"写"入口。这让"插件不会改你的数据库"成为可验证的物理事实。

2. **"无别名"架构。** 画布节点的 `source` 直接是 `'design'` 或 db id（如 `'db1'`），不存在 `d1` / `b1` 中间层。`DESIGN_SOURCE = 'design'` 是 `shared/canvas.ts` 的常量。这意味着引用、统计、导出、对比都只走一种结构，少一类一致性 bug。

3. **撤销栈基于"动作"而非"文件"。** `CanvasSession.applyChange(change)` 把 DesignOp + 布局 op + 文件副作用打包成一个 `DesignChange`，进同一个撤销条目。这让"删一个分区（同时删内容 + 改 layout）"可以一次 Ctrl+Z 全回滚。

4. **协议是宿主权威。** webview 永远不直接落盘；任何"我选了 7 张表"都是发 key，主进程按自己的 ModelStore 重新求值。导出里这点尤其严：`ExportRequest` 只列元数据 + 路径，**不**带表结构。

5. **shared 是测试的根。** 绝大部分纯逻辑（画布 ops、剪贴板、命名空间、ER 解析、ER 同步、字段解析、tbls URL/校验、export builder、normalize、diff）都在 shared + 子模块里，并且有对应 vitest。`export/builder.ts` 显式不 import vscode 是这一原则的极端例子。

6. **错误带 `action` 字段。** tbls / 下载失败不让 UI 自己造文案，错误里 `action: 'install' | 'pickPath' | 'releases'` 决定通知里出现哪几个按钮。这把"易错路径"从字符串模板变成了可枚举的协议。

## 5. 优化点分析

> 标签：**[架构]** = 涉及层间关系要小心；**[功能]** = 用户看得见；**[性能]** = 大数据量才显著；**[DX]** = 开发者体验；**[测试]** = 测试覆盖。重要度 ★ / ★★ / ★★★。

### 5.1 架构层面

| # | 优化点 | 标签 | 重要度 | 说明 / 风险 |
|:--|:--|:--|:--:|:--|
| A1 | **Webview 状态机显式化** | [架构] | ★★ | 现在 `App.vue` 用 `onMounted` 装 `onHostMessage` 监听器，内部靠 `state.exportRequest` / `state.editDiagram` / `state.selectRequest` / `state.focus` 等"现成字段"作为"我刚收到一条消息，做点事"的触发器。问题是**这些字段既承担状态、又承担事件**，导出对话框的"打开-响应"和"结果回调"混在同一个 `exportRequest` 上，状态机在组件里用 if/else 写死。提出一个独立的 `commands: { id, kind, startedAt }` 队列 + 一个 `results: Map<id, Result>`，让 webview 知道自己"正在等哪个命令的回复"，同时给"我先发 open 再发 pickPath 再发 run"这类串联操作一个统一通道。 |
| A2 | **共享内核补 `index.ts` 边界检查** | [DX] [测试] | ★ | `src/shared/` 不准 import vscode 这条规则当前靠 review。可在 `shared/index.ts` 顶部加 `// if you add an `import * as vscode` here, the test below will catch it`，然后在 `test/sharedBoundary.test.ts` 用 `ts.transpile` 扫描 `shared/**/*.ts` 找 `from 'vscode'`。 |
| A3 | **`Harness` 接口的松耦合方向** | [架构] | ★★ | 现在 `Harness` 是个把 storage / store / tree / canvases / connections / editors / diagrams 全揉一起的接口，**所有命令都从 `commands/common.ts` 拿**，新增命令时很难知道"我到底需要哪些依赖"。建议分两层：`HarnessCore`（storage、store、diagrams、canvases、tree、treeView），`HarnessUI` = `Core + connections + editors`。`commands/*` 改成只声明自己需要的子集，能编译期挡掉"在新命令里意外引到 UI 模块"。 |
| A4 | **`extension.ts` 装配逻辑下沉到 factories** | [DX] | ★ | `extension.ts` 现在 60+ 行装配 + StorageWatcher 内部类。装配本身就是测试的难点（无法对"按依赖连起来"做断言）。提一个 `buildHarness(context): Harness` 出来，把 watcher / ensure / 注册顺序都搬进去，activate 瘦身到 5 行。 |
| A5 | **协议多文件收敛** | [DX] | ★ | 现在 `protocol.ts` / `diagramProtocol.ts` / `connectionProtocol.ts` / `editProtocol.ts` 四个文件，导出类型散落。`src/shared/messages.ts` 一个文件按视图分块写 `export type HostMessage = CanvasHostMessage \| DiagramHostMessage \| ...`，让"消息总览"可以一搜就有。 |

### 5.2 性能 / 大数据

| # | 优化点 | 标签 | 重要度 | 说明 |
|:--|:--|:--:|:--:|:--|
| P1 | **`ModelStore` 失效粒度** | [性能] | ★★ | `store.invalidate({})` 一次性把全部缓存作废。一次"保存 schema.json"会连带让所有打开的画布重算 `comparison()`。`comparisons.json` 自己没改时本可以原地复用。建议把 `invalidate` 分两类：真改动 = 全清；同设计外部文件触碰 = 只清 `comparison` 缓存，schema/ext 不动。 |
| P2 | **画布 viewModel 全量重算** | [性能] | ★★ | `webview-ui/src/canvas/viewModel.ts buildView` 每次都从根生成"全部层"。一次选中/聚焦也走完整管道。当画布大到几百节点时，右侧属性面板每点一次都会让左侧 tree / 画布重渲。`App.vue` 现在靠 `shallowRef` 兜底，但 viewModel 仍是全量。引入按 `state.level` 切片的增量构建（root 不变就跳过 root，重算当前层 children）。 |
| P3 | **大型画布的初始 ELK 布局** | [性能] | ★★ | `canvas/layout.ts layoutLevel` 对多层用 INCLUDE_CHILDREN 一次算完，画布 500+ 节点时肉眼可见的卡顿。可分两阶段：先把分区框当作普通节点算位置（快），再为每个未折叠分区递归算子图（并发或按需）。 |
| P4 | **导出 builder 一次性扫两遍** | [性能] | ★ | `export/builder.ts` 的"先算路径、再渲染"两趟算法对小数据无感（< 50 表），1000 表时内存会同时持有一份完整表数据 + 一份完整 Markdown 文本。两趟可以合并：渲染当前表时只依赖"已知文件路径表"，未知链接先写 `???`，全部路径算完后再做一次字符串替换。 |
| P5 | **`fsUtil` 一次性读目录** | [性能] | ★ | `storage.ts` 里"列目录 + 读元数据"反复用 `vscode.workspace.fs.readDirectory`，每个文件都走 round-trip。能跑通是因为只有 1-2 个文件场景，**几十张表的工作区会显著变慢**。可以一次性读目录 + 缓存 schema.json 的 mtime，只在 mtime 变化时重读。 |
| P6 | **侧边栏树按需展开** | [性能] | ★★ | `workspaceTree.ts` 一次 `getChildren(workspace)` 把所有设计 / 分区 / 表 / 字段全算出来。VS Code 的 TreeDataProvider 本来就支持按 `resolveTreeItem` 懒加载。改成只有"展开了才发子节点"能显著减小初次显示耗时（但要小心 `reveal` 的语义）。 |

### 5.3 功能层面

| # | 优化点 | 标签 | 重要度 | 说明 |
|:--|:--|:--:|:--:|:--|
| F1 | **导出增量 / 增量对比** | [功能] | ★★★ | 当前导出一律"全量重新生成"。对一个每次只要"把今天改的告诉 AI"的场景太重。给 manifest 加 `version + contentHash`（表内容 + frontmatter），主进程对比后**只发 changed files**，对接到"复制给 AI"按钮就是"增量剪贴板"。 |
| F2 | **导出支持按画布"快照模式"** | [功能] | ★★ | 当前 `export/run` 走 `h.canvases.layout()`，也就是说**只导出当前编辑器里的画布**。如果用户开了 3 个画布，导出也只能导一个。设计库是稳定单位 —— 改成"按 design id"，每个 design 可独立 export，并把结果落在 `设计库/<id>/...` 一层下。 |
| F3 | **导出"按 SQL 视角"模式** | [功能] | ★★ | 现在 README 给的是 ER 图 + Markdown 表。AI 经常需要的是"在 postgres 里怎么 CREATE TABLE"。给导出加 `--as-sql` 开关，把表文件渲染成 `CREATE TABLE … ;` 块，关系文件是 `ALTER TABLE … ADD CONSTRAINT … ;`。这样 AI 拿过去就能跑。 |
| F4 | **导出按命名空间合并** | [功能] | ★ | 现在 `_未分组` 走专门目录，但有命名空间的画布里仍然每层有独立 README。当 AI 只关心"这个设计库有哪些表"时，根 README 加一个"扁平表清单（按命名空间分组）"会好用很多。 |
| F5 | **属性面板的"批量编辑"** | [功能] | ★★ | 选中多张表 / 多个字段时，右栏还是单选模式。多选时只显示共有的可改字段（`isNullable` / `comment` / `comment`），点"应用到 N 项"一次写回。设计库场景"给这 10 张表都加 created_at 字段"今天要操作 10 次。 |
| F6 | **设计图"复制为 prompt"模板** | [功能] | ★ | `media/spec/mermaid-design.md` 是写死的。可以让用户在"复制给 AI"时选 prompt 模板（"帮我改 ER 图" / "我打算加 X，帮我看看影响" / "生成 SQL"），每个模板一段前置说明 + 留白。 |
| F7 | **数据源面板直接拖表到画布** | [功能] | ★ | 这是 README"已知限制"里的第一条。从 `SourcePanel.vue` 的表行开 `dataTransfer`，目标 `CanvasView` 的 drop handler 复用 `items/move` 协议，比现在"右键 → 添加到画布"少两步。 |
| F8 | **Ctrl+F 搜索表** | [功能] | ★ | 同 README"已知限制"。已有 `SourcePanel.vue` 的 `search` ref，搬到 `Ctrl+F` 命令 + 一个简单的 quickpick 就能用。 |
| F9 | **改名检测** | [功能] | ★★ | diff 当前不识别 rename。给 `diff/diff.ts` 加一个轻量 fuzzy（编辑距离 ≤ 2 且表名只差大小写 / 单复数），识别出来后当作"rename"而不是"add+remove"，差异数量立刻少很多。 |
| F10 | **设计图 → 表结构** 支持 non-ER 类型 | [功能] | ★★ | 现在只有 ER 能 sync。状态图、时序图里**经常**会暗含"我打算加这张表"和"我打算加这个字段"。把 `computeErSync` 重构为 `parseIntentFromDiagram(type, code) → SyncItem[]`，各类型实现自己的解析（状态图提取 `状态名 → ID 字段`），共用 apply 路径。 |

## 7. 风险记录

- **`activationEvents: ["*"]`** 是有意保留，**不要**收窄（见 `docs/当前实现文档/README.md` 约定段）。
- **`webview-ui/tsconfig.json` 不应有 `baseUrl`**（TS 7.0 会失效）。当前已修复，新增 webview 字段请用 `paths` 相对路径。
- **`store.dbName()` 仍然存在且会被误用**。新代码如要展示数据库标识，请用 `LoadedSource.id` 或 `ws.db(id).readMeta().name`，不要走 `dbName`。
- **导出 `requestId` 一定由主进程签发**，webview 只回传 —— 0.0.5 修过一次这个 bug（参见 `docs/当前实现文档/README.md` 已知限制段）。
- **协议加字段时同步两边**：`src/shared/protocol.ts` + `webview-ui/src/store.ts` 的 `case` + `dev/mockHost.ts` 的 `case`，少一处 = 静默丢消息。
