# 03 分析：tbls 只能读取表结构吗？能读取表里的数据吗？

> 已确认：本次**不读取表里的数据**。本文只作为分析记录，第四节的方案留到以后需要时再评估。

## 一、结论

**tbls 只读取结构信息（元数据），不读取、也不输出表里的数据。** 它的定位是"给数据库生成文档的工具"，所有子命令都围绕结构展开。

唯一的例外是 MongoDB 这类没有固定结构的数据源：tbls 会抽样读取一些文档来推断有哪些字段，但输出的仍然只是推断出来的结构，不包含数据本身。

如果以后需要读取数据（例如行数、样例数据、校验逻辑关系），需要另外实现，方案见第四节。

## 二、依据

### 2.1 子命令

在本机的 tbls 1.96.0 上执行 `tbls --help`，可用的子命令是：

| 子命令 | 作用 | 和数据的关系 |
| :-- | :-- | :-- |
| `doc` | 生成 Markdown 文档和 ER 图 | 只有结构 |
| `out` | 按指定格式输出结构（json、yaml、dot、plantuml、mermaid、xlsx 等） | 只有结构 |
| `diff` | 比较数据库和文档，或者两个数据库之间的结构差异 | 只有结构 |
| `lint` | 按规则检查结构，例如"每张表都要有注释"、"每张表都要有主键" | 只有结构 |
| `coverage` | 统计有多少表和字段写了注释 | 只有结构 |
| `ls` | 列出表 | 只有结构 |
| `completion`、`version`、`help` | 辅助命令 | — |

**没有执行 SQL 查询的命令**，也没有"导出数据"、"查看前几行"之类的选项。`out` 的参数只有输出格式、包含和排除哪些表、按标签或视点筛选、关联距离，全部是筛选结构用的。

### 2.2 输出格式

`tbls out -t json` 的 JSON 格式（官方 JSON Schema：`spec/tbls.schema.json_schema.json`，插件里对应 `src/shared/tbls.ts`）只包含以下内容：

| 内容 | 字段 |
| :-- | :-- |
| 库 | `name`、`desc`、`driver`（数据库类型、版本、当前 schema、search_path） |
| 表和视图 | `tables[]`：名称、类型（表、视图、物化视图等）、注释、建表语句或视图定义 `def` |
| 字段 | `columns[]`：名称、类型、是否可空、默认值、`extra_def`（如自增）、注释 |
| 索引 | `indexes[]`：名称、定义、字段 |
| 约束 | `constraints[]`：主键、外键、唯一、检查约束 |
| 触发器 | `triggers[]`：名称、定义 |
| 关系 | `relations[]`：来自外键，或者 `.tbls.yml` 里声明的虚拟关系；基数 |
| 函数、存储过程 | `functions[]`：名称、参数、返回类型 |
| 枚举 | `enums[]`：PostgreSQL 的枚举类型及取值（这是类型定义，不是表数据） |
| 标签、视点 | `labels`、`viewpoints`：来自 `.tbls.yml` |

**没有**行数、表大小、样例数据、字段取值分布这类信息。关系的基数（一对一、一对多）是根据字段是否可空、是否唯一推算出来的，不是统计数据得出的。

### 2.3 官方文档

- tbls 的自我介绍是"CI-Friendly tool to document a database"，即给数据库写文档的工具。
- 在 BigQuery 的说明里，tbls 需要的权限只有 `bigquery.datasets.get`、`bigquery.tables.get`、`bigquery.tables.list`，全是读取元数据的权限，没有读取数据的权限（`bigquery.tables.getData`）。这从侧面说明 tbls 不读取数据。
- MongoDB 的连接串支持 `sampleSize` 参数（例如 `?sampleSize=20`），表示抽样多少条文档来推断字段。这是前面说的例外。

### 2.4 扩展机制

tbls 支持外部驱动：如果系统里有名为 `tbls-driver-foodb` 的可执行文件，tbls 就能识别 `foodb://` 开头的连接串。外部驱动通过环境变量 `TBLS_DSN` 拿到连接串，向标准输出打印符合 tbls JSON 格式的结构。

这个机制可以用来接入 tbls 原生不支持的数据库（比如 Oracle），但它的输出格式仍然只能表达结构，不能用来读取数据。

## 三、对本项目的影响

### 3.1 好的一面

- **只读账号完全够用。** 连接页面可以放心地建议用户使用只读账号，甚至是只有元数据权限的账号。
- **快照里没有业务数据。** 快照文件、画布、差异结果都不包含用户数据，不会因为同步结构而把个人信息、订单金额之类的内容落到本地磁盘。
- **以后的 MCP 接口可以放心地把结构提供给 AI**，不用担心泄露业务数据。

### 3.2 做不到的事

只靠 tbls，下面这些功能做不了：

| 想做的事 | 需要的数据 |
| :-- | :-- |
| 在画布上显示每张表有多少行 | 行数（或者数据库统计信息里的估算值） |
| 点开一张表看前几行数据 | 样例数据 |
| 查看字典表的内容（关系类型 `dictionary`） | 字典表的全部行 |
| 校验逻辑关系：子表里有多少行找不到对应的父表记录 | 执行统计查询 |
| 分析 JSON 数组字段里实际存的是什么 | 抽样数据 |
| 判断一个字段实际上是不是唯一的、是不是从来没有空值 | 执行统计查询 |

其中"校验逻辑关系"和本项目关系最密切：设计模型里标记为 `logical`、`json_array` 的关系在数据库里没有外键约束，现在只能看到"设计上认为有关系"，无法知道真实数据是否遵守了这个关系。

## 四、如果以后需要读取数据

### 4.1 可选方案

| 方案 | 做法 | 优点 | 缺点 |
| :-- | :-- | :-- | :-- |
| A. 插件内置 Node.js 数据库驱动 | 用 `pg`、`mysql2`、`tedious`（SQL Server）等纯 JavaScript 驱动，在插件主进程里直接查询 | 不依赖外部程序；可以精确控制只读事务、超时、行数上限 | 每种数据库要单独接入；SQLite 的常用驱动是原生模块，要按平台打包，或者改用 WebAssembly 版本；插件体积变大 |
| B. 调用 usql | usql 是一个通用的命令行 SQL 客户端，和 tbls 一样用 Go 编写，连接串格式也基本一致 | 支持的数据库和 tbls 接近，一个工具覆盖多种数据库 | 又多一个需要用户安装的外部程序；输出格式和错误信息需要逐个适配；是否支持稳定的 JSON 输出需要验证 |
| C. 自己用 Go 写一个小工具 | 复用 tbls 使用的数据库驱动，只提供"执行只读查询并输出 JSON"的功能，随插件分发 | 连接串格式和 tbls 完全一致 | 要维护一个 Go 项目，并为 Windows、macOS、Linux 分别编译 |
| D. 交给 Cursor 里的数据库 MCP | 用户自己在 Cursor 里配置数据库相关的 MCP，AI 直接查询 | 插件不用写代码 | 连接信息要另外配置在 MCP 里，违背"连接信息只保存在系统凭据中、永远不交给 AI"的要求 |

### 4.2 建议

- **本次不做。** 这次的改动集中在减少输入和连接页面上。
- 如果要做，建议**方案 A**，先支持 PostgreSQL 和 MySQL（这两种都有成熟的纯 JavaScript 驱动），其他数据库按需增加。连接信息直接复用连接页面保存的 `ConnectionProfile`，不需要用户再配置一次。
- 必须满足的安全要求：
  1. **默认关闭**，每个数据库数据源单独开启"允许读取数据"。
  2. 所有查询都在只读事务里执行（PostgreSQL 用 `BEGIN READ ONLY`，MySQL 用 `START TRANSACTION READ ONLY`），并设置语句超时和返回行数上限。
  3. 只执行插件内置的几类查询（行数、样例数据、关系校验），不提供任意 SQL 输入框。
  4. 查询结果只显示在界面上，**不写入任何文件**，也不自动提供给 MCP 或 AI。需要给 AI 的只有统计结果（例如"有 12 行找不到父记录"），不包含具体的数据行。
- 行数有一个成本更低的做法：PostgreSQL 的 `pg_class.reltuples`、MySQL 的 `information_schema.tables.table_rows` 都是数据库自己维护的估算值，读取它们不需要扫描表。可以作为方案 A 的第一个功能。
